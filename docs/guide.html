One stylesheet. Your HTML.

Copy dist/sprig.css beside your HTML, then use the snippet below. No package installation is needed to use the CSS. This is a local preview release; the package name is not a published-install promise.

<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8">
    <meta name="viewport" content="width=device-width, initial-scale=1">
    <meta name="color-scheme" content="light dark">
    <link rel="stylesheet" href="sprig.css">
    <title>A good beginning</title>
  </head>
  <body>
    <main>
      <h1>Hello, good things.</h1>
      <p>Start small. Make it yours.</p>
    </main>
  </body>
</html>

Sprig is an opinionated, global starting point for new pages—not a scoped widget library. It is independently rewritten, not drop-in Pico compatibility. Change --pico-* overrides to Sprig tokens and review old custom classes. See the migration notes.

Let the elements do their thing.

Forms and actions

Inputs, textareas, and selects receive full-width styling. Checkboxes and radios stay native. Use a persistent label, explicit button types, autocomplete where appropriate, and help/error text connected with aria-describedby.

Buttons support data-variant="quiet" and data-variant="danger". Set aria-busy="true" for a loading indicator, keep the action’s text, and prevent duplicate work in application code. Native disabled prevents interaction; aria-disabled alone does not.

Navigation is still a link. Do not change a link to role="button" just to style it. Add an application class if a navigation CTA needs a filled treatment.

Cards and disclosures

An article gets a surface, a border, and padding. Its direct header/footer get spacing. A native details with a summary is a complete disclosure; no JavaScript required. Use data-callout="note" or "danger" for an aside, and data-badge for a small label.

Color alone is never an error message. Say what happened and how to fix it.

Tables

Use a caption, header cells, and scope="col"/scope="row". Put wide tables in a named, focusable .overflow region; do not squeeze away their relationships.

Dialogs and popovers

Give dialogs an accessible name. Call showModal() to get modal focus behavior; toggling the open attribute is not equivalent. Provide a visible close action (a form with method="dialog" works) and test Escape and focus return.

Native popovers use popover and popovertarget. They are nonmodal: don’t use them where a modal is required. Older browsers need an explicit fallback such as details; CSS cannot polyfill behavior.

Optional anchor positioning: wrap one trigger/popover pair in data-anchor-scope, put data-anchor on the trigger and data-anchored on the popover. Browsers supporting both anchor positioning and scoping place it near the trigger; others keep the native centered popover. Each pair needs its own wrapper.

A theme is a few decisions.

The OS preference is the default. Set data-theme="light" or "dark" on html to override it. Remove the attribute to return to automatic. Sprig’s stylesheet needs no JavaScript; only a user-facing theme toggle needs state handling.

/* Your application CSS, loaded after Sprig. */
:root {
  --sprig-accent: #3b526f;
  --sprig-on-accent: #ffffff;
  --sprig-radius: .25rem;
  --sprig-width: 68rem;
}
:root[data-theme="dark"] {
  --sprig-accent: #b7cee8;
  --sprig-on-accent: #192736;
}
@media (prefers-color-scheme: dark) {
  :root:not([data-theme="light"]) {
    --sprig-accent: #b7cee8;
    --sprig-on-accent: #192736;
  }
}

Use unlayered application CSS so your overrides win without specificity games. The ordered layers are sprig.tokens, sprig.base, sprig.layout, sprig.forms, and sprig.components.

The semantic color roles are bg, surface, soft, text, muted, line, control, accent, on-accent, danger, and focus; all have the --sprig- prefix. Layout/type tokens are radius, space, width, column, font, and mono. Change foreground/background pairs together and retest contrast in both themes. line is decorative; control is the stronger boundary for interactive controls.

Small tools. Honest boundaries.

Development tools require Node 22 or newer. Run these from the repository root, or use the equivalent CLI bin from an installed local tarball. CSS users need no Node.

# Full, deterministic build
node bin/sprig.js build --all --out sprig.css

# Union of modules used by static pages
node bin/sprig.js build --html index.html --html about.html --out pages.css

# Keep modules needed by runtime-rendered content
node bin/sprig.js build --html index.html --include forms,overlays

# Find patterns and read the vocabulary
node bin/sprig.js recipe "accessible contact form" --json
node bin/sprig.js contract

# A few common mistakes, not an accessibility certification
node bin/sprig.js check examples/starter.html --json

The packer selects whole modules: tokens, base, and layout are always kept; buttons, forms, cards, tables, and overlays are selected by static tags/attributes. It does not execute templates, understand JSX, follow JavaScript, or purge selectors. For those cases, use the full CSS or explicit --include. There is no minifier or native compiler in this release.

Existing output files are protected. Use --force only when you intend to overwrite. Builds refuse to overwrite their HTML inputs. The static checker catches missing labels/alt attributes, missing ID references, duplicate IDs, unnamed dialogs, and a few action pitfalls. It can miss real problems and misread malformed/templates markup. It is not a parser-grade HTML validator or a screen reader.

Exit codes: 0 completed, 1 lint findings, 2 invocation/file errors. JSON reports go to stdout; invocation errors go to stderr.

Give your collaborator a map.

The Sprig skill is a small, provider-independent workflow. Read the contract, retrieve a relevant recipe, implement, then verify the actual interface. The llms.txt entry point points to the same sources humans use.

No API key, model call, telemetry, generated “design intelligence,” or hidden network request. Copy the skill into your agent’s supported skills directory if you want to install it; nothing writes to your harness automatically.

Good bones, realistic promises.

Target: current stable Chromium, Firefox, and Safari, with cascade layers and modern selectors. The default palette includes hex fallbacks before OKLCH enhancement. Unsupported text balancing and anchor positioning fall back harmlessly. Popover behavior requires a supporting browser or an explicit application fallback. No IE or pre-cascade-layer support is promised.

The repository has automated Chromium interaction/accessibility tests and responsive checks. This does not establish cross-browser or WCAG conformance. Test your own content with keyboard navigation, zoom, assistive technology, forced colors, and your browser support matrix. CSS cannot make bad semantics or broken application behavior accessible.

This is a 0.1 prototype: useful and testable, but not a mature replacement for every Pico feature. There is no switch component, tooltip abstraction, framework adapter, scoped mode, or drop-in migration shim.
